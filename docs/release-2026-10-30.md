Подготовка исходников не запускает обновление VPS. Сначала ручная проверка
@botToPract696_bot в облаке, затем публикация согласованного кода в GitHub,

## Ручная проверка текущих правок — около 10 минут плюс поиск

1. Под администратором тестового коллектива откройте `/catalog` → «Найти песни
   в интернете». Начните **новый** поиск исполнителя с обычными песнями, Live,
   Remix и feat-кредитами. Уже открытый ранее отбор сохраняет прежний выбор.
   Поиск может занять 20–30 минут; выдача из кэша быстрее.
2. В первой таблице проверьте время каждой строки, включая зачёркнутые. При
   неизвестном времени должна быть просьба указать его. `(feat. …)` виден.
   Remix без галочки; у пары обычная/Live выбрана Live, обычная исключена.
3. Включите один ремикс, выключите и верните другую песню. Перейдите вперёд/назад.
   Выбор должен сохраниться. Повторное открытие не возвращает исходные галочки.
4. Нажмите «Продолжить». В итоговой таблице нет исключённых песен и feat-кредитов.
   Live исчезает, если итоговое название свободно. Вернитесь и выберите обе версии:
   в следующем предпросмотре обычная и Live должны оставаться различимыми.
   Название ремикса сохраняет `(Remix)`.
5. Отмените один отбор — каталог не меняется. Подтвердите другой: добавляется
   именно итоговый состав, существующие песни не перезаписываются. Повторное
   нажатие подтверждения не создаёт копии. Через `/catalog` проверьте названия/время.
6. Для утверждённого тестового списка скачайте оба PDF: музыкантам и световику.
   Проверьте RU/EN и транслитерацию. Нет статуса, автора и сведений об одобрении;
   группа, дата, город, песни, длительности и подпись бота остаются.
   Запросите PDF также через старую кнопку экспорта: должен сформироваться новый
   макет без статуса. Уже скачанный старый документ не изменяется.
7. В сообщениях Telegram одобрение и имя одобрившего должны остаться.
   Article-стиль по-прежнему с тремя столбцами; точная ширина первого зависит от Telegram.

## Что переносится

Только исходники, зависимости, миграции и документация. Целевая схема:
`d89c3e17a024 → e62f4a91b830 → f71a9c802d34 → a82cd901be45`.
Последние правки отбора/PDF отдельной миграции не требуют; макет PDF — 5.

`.env`, `.env.admin`, токены, дампы, тома PostgreSQL и содержимое баз не публикуются
и между контурами не копируются. Каждый контур мигрирует **свою существующую базу**.
Рабочие песни, выступления, права и черновики должны сохраниться. Значения новых
настроек по умолчанию: mono, предложения разрешены участникам, username пустой до
наблюдения настоящего Telegram Update. Резервные копии остаются на своём VPS.

## Порядок обновления VPS — выполнять после публикации выпуска в GitHub

Один сервер: `212.192.217.128`. Сначала `/opt/setlist_bot_sandbox` (ветка
`feature/web-admin`), затем `/opt/setlist_bot_codex` (`main`). Оба checkout должны
указывать на согласованный и проверенный выпуск. Не запускайте сборки параллельно
на VPS с 2 ГБ памяти. Не используйте `down -v`, `reset --hard` или перенос дампа из облака.

### 1. Обновить серверную песочницу, пока polling остаётся в облаке

```bash
(
  set -e
  cd /opt/setlist_bot_sandbox
  test -z "$(git status --porcelain)"
  git pull --ff-only origin feature/web-admin
  git log -1 --oneline
  bash scripts/update-sandbox-admin.sh cloud
)
```

Скрипт сохраняет серверную тестовую БД, мигрирует её, проверяет схему, поднимает
admin и оставляет серверный test polling остановленным. Основной бот работает.
Обновлённая админка до миграции production временно покажет несовместимую схему
основного раздела; это не означает остановку основного Telegram-бота.

### 2. Перенести тестовый polling на VPS и проверить

Сначала оператор Codex останавливает **облачный тестовый** polling и сообщает
об этом. Только затем на VPS:

```bash
cd /opt/setlist_bot_sandbox
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml \
  -f compose.admin.production-access.yaml up -d --no-build --no-deps bot
docker compose -f compose.sandbox.yaml exec -T bot .venv/bin/setlist-bot --check
docker compose -f compose.sandbox.yaml logs --tail 30 bot
```

Ожидаются `PostgreSQL OK; migration a82cd901be45` и polling @botToPract696_bot.
Данные будут из прежней серверной песочницы. Облачная БД не переносится.
Повторите ручную проверку импорта/PDF и накопленных сценариев, проверьте админку.

### 3. Обновить production после успешной серверной проверки

```bash
(
  set -e
  cd /opt/setlist_bot_codex
  test -z "$(git status --porcelain)"
  git pull --ff-only origin main
  git log -1 --oneline
  bash scripts/release-production.sh
)
```

Скрипт делает backup основной БД и репетирует миграцию **на временной копии этой
же основной базы на VPS**, проверяя количество рабочих записей. Только после успеха
останавливает основной bot, делает свежую копию, применяет миграции к `setlist`
и запускает bot. Тестовые данные здесь не участвуют; дамп в рабочую БД не восстанавливается.
При ошибке после остановки остановитесь и сохраните вывод, не делайте downgrade
или восстановление поверх рабочей базы без разбора ошибки.

### 4. Обновить доступ production-админки к новым таблицам

Через 30 секунд после запуска основного бота:

```bash
cd /opt/setlist_bot_sandbox
python3 scripts/connect-production-admin.py --enable-actions
```

В этом выпуске появились `ux_events`/`ux_daily`, поэтому существующей выделенной
SQL-роли нужны права чтения новых таблиц. Скрипт повторно настраивает ограниченные
права, сохраняет прежние секреты и пароль входа, делает локальную копию `.env.admin`
и пересоздаёт только admin со всеми тремя Compose-файлами. Он **не меняет владельца
коллектива**, не копирует бот-токен и не переносит данные.
Если требуется режим просмотра, запускайте без `--enable-actions`.

Через прежний SSH-туннель откройте `http://127.0.0.1:8088`. Проверьте два контура,
схему a82cd901be45, правильные ID ботов, мониторинг, каталог, поддержку и UX.
В production проверьте `/concerts`, существующие данные и свежий PDF.
