# Тестовый выпуск: единая команда, контекст сообщений и подмены

Ветка: `codex/team-membership-context`. Схема: `e52b8f139a60`.
Сначала проверяется тестовый бот; merge в main и выпуск основного бота — отдельно.

## Поведение

- Постоянная команда и `/members` показывают единое членство, профессиональные роли,
  заявки, приглашения и административные права. Роль менеджера не выдаёт права admin.
- Добавление администратором отправляет приглашение с ролями. Принятие даёт обычное
  членство и доступ к коллективу в `/groups`, без повторного `/register`.
- `/register` остаётся самостоятельной заявкой. Одобрение даёт тот же результат.
  Совпадающие встречные заявка и приглашение используют уже выраженное согласие обеих
  сторон. Изменение предложения делает старые кнопки недействительными.
- Новые роли активного участника требуют согласия. Отказ сохраняет текущие роли/права.
  Снятие роли уведомляет участника, но не прекращает членство, даже если это последняя роль.
- Исключение/выход требуют подтверждения. Обычного участника исключает администратор,
  администратора — владелец; самостоятельный выход доступен и администратору.
  Владелец сначала передаёт владение. Подтверждённые будущие выступления перечисляются
  до выхода и сохраняются; отменять их надо отдельно. История и личные черновики не удаляются.
  Доступ к данным коллектива после выхода закрывается, гостевой доступ к своим участиям сохраняется.
- Приглашение на выступление подтверждает только это выступление. Сохранение шаблона
  не оформляет членство: явно заданный кандидат может использоваться в шаблоне, если
  нет подходящего постоянного исполнителя. Само применение шаблона не отправляет приглашений.
- Подмена себя администратором завершает согласие и утверждение одной транзакцией.
  Занятость проверяется, её игнорирование требует отдельного явного действия.
  Для другого кандидата сохраняются согласие и утверждение администратором.
  В составе видны запрос подмены и ожидающий утверждения кандидат.
- Ответы Telegram подписаны коллективом, выступлением или областью календаря.
  Исключение: карточка песни/меню редактирования непосредственно под исходным каталогом
  того же коллектива. Проверяется реальный ID отправленного сообщения; при промежутке
  подпись сохраняется. Нажатия на названия внутри таблицы сохранены.

## Миграция

Действующие членства, административные права, профили, бронирования и история сохраняются.
Старые постоянные контакты без активного членства получают приглашение с прежними ролями.
До принятия они остаются контактами, а после принятия восстанавливаются их приоритеты.
Старое согласие на выступление не превращается в согласие вступить в коллектив.
При недоставке администратор получает сообщение; участник должен запустить бота,
после чего администратор повторяет отправку из команды. Приглашения также доступны в `/groups`.

Приглашения действуют 30 дней, привязаны к версии членства и жизненному циклу коллектива.
Перед принятием и доставкой повторно проверяются адресат и действующие права отправителя.
Удаление/восстановление коллектива не оживляет старые приглашения.
Миграция не выдаёт административные права новым людям. Рабочий токен не меняется.

Откат схемы блокируется, если уже появились приглашения или история выхода:
для полного отката используется резервная копия, а не потеря этих данных.
Скрипт обновления делает резервную копию до миграции.

## Обновление тестового контура на VPS

```bash
(
  set -e
  cd /opt/setlist_bot_sandbox
  test -z "$(git status --porcelain)"
  git fetch origin codex/team-membership-context
  git switch codex/team-membership-context
  git pull --ff-only origin codex/team-membership-context
  bash scripts/update-sandbox-admin.sh server
)
```

Запускать только в `/opt/setlist_bot_sandbox`. Скрипт проверяет ID тестового бота,
собирает образ, останавливает старые службы, делает backup, применяет миграции,
проверяет схему/health и поднимает службы. Второй polling вручную не запускать.
При ошибке не продолжать команды по отдельности; сначала проверить сообщение скрипта.
Обновление может отправить приглашения старым постоянным контактам от тестового бота.

## Ручная приёмка

1. Пригласить нового человека как менеджера и световика. До принятия доступа нет;
   после — один участник с двумя ролями и коллектив в `/groups`.
2. Отклонить новые роли уже принятого участника: старые роли и доступ остаются.
3. Подать `/register`, одобрить; проверить тот же результат. Проверить встречное приглашение.
4. Снять последнюю роль: участник остаётся. Исключить/выйти с будущим выступлением:
   коллектив исчезает из `/groups`, подтверждённое участие остаётся в `/my_gigs`.
5. Повторить исходный сценарий подмены себя; состав показывает администратора,
   прежний исполнитель получает уведомление об освобождении.
6. Проверить другого кандидата: согласие, видимое ожидание, отдельное утверждение.
7. Открыть каталог, песню и редактирование на iPhone и Mac; повторить с сообщением
   между таблицей и карточкой, а также со второй страницей каталога.
8. Переключить коллектив и открыть старые кнопки команды/песни: подпись относится
   к исходному объекту. Проверить RU/EN, пустые ответы, архивирование и календарные ссылки.

Автоматические проверки выполняются на отдельной PostgreSQL-базе `setlist_test`,
без настоящего Telegram-токена и отправки сообщений. См. `CONTRIBUTING.md`.
