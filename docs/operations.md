# Запуск, обновление и хранение данных

## Что сохраняется в GitHub

Репозиторий содержит исходники, миграции, lock-файл зависимостей, тесты, CI и
документацию. Он не содержит рабочую базу, Telegram-токен или резервные копии.
Токен передаётся через `.env` либо окружение, пример без секрета — `.env.example`.

На момент первого коммита бот запущен в Docker в рабочем облачном окружении Codex.
Это окружение не является настроенным постоянным хостингом: его непрерывная работа
после закрытия сессии не гарантируется. Push в GitHub не выполняет деплой.
Для работы круглосуточно нужен отдельный постоянно доступный сервер и перенос данных.
Выбор хостинга и автоматизация развёртывания пока не согласованы.

## Развёртывание

Базовый сценарий Docker Compose описан в [README](../README.md). Compose-конфигурация
поставляется для разработки: параметры PostgreSQL заданы явно и требуют отдельной
настройки перед использованием на постоянном сервере.

```bash
docker compose up --build -d
docker compose ps -a
docker compose exec -T bot .venv/bin/setlist-bot --check
```

Сервис `migrate` применяет Alembic-миграции до запуска бота. В приложении используется
polling: на один токен должен работать только один процесс. При переносе на новый
сервер сначала остановите прежний процесс. `restart: unless-stopped` перезапускает
контейнер только при работающем Docker и сохранённом окружении; он не создаёт хостинг.

Если сеть требует доверенный TLS-прокси, используйте `compose.proxy.yaml` и публичный
CA bundle по инструкции README. Проверка сертификатов остаётся включённой.

## Обновление

До изменения схемы сохраните резервную копию. Для простого обновления с паузой в работе:

```bash
docker compose build
docker compose stop bot
docker compose run --rm --no-deps migrate
docker compose up -d --no-build bot
docker compose exec -T bot .venv/bin/setlist-bot --check
docker compose logs --tail 30 bot
```

Эти команды выполняются из каталога нужной версии кода. При использовании TLS-override
применяйте те же `-f compose.yaml -f compose.proxy.yaml` ко всем вызовам Compose.
При ошибке миграции разберитесь с ней до запуска новой версии. Откат кода не означает
безопасный откат схемы: отдельные миграции защищают данные от потери при downgrade.

При старте бот проверяет и синхронизирует команды Telegram до начала polling.
Отдельная команда `setlist-bot --sync-commands` обновляет только меню и не запускает
второй polling-процесс. Области видимости, языки и дополнительные исторические
регистрации описаны в разделе «Меню команд Telegram» README.

## PostgreSQL и резервные копии

Данные хранятся в Docker-томе `postgres_data`; его полное имя зависит от имени
Compose-проекта. Пересоздание контейнера сохраняет том. `docker compose down -v`
удаляет его; эту команду нельзя использовать для обычного обновления.

Полный дамп, включая личные черновики и служебные связи, можно сохранить так:

```bash
mkdir -p backups
chmod 700 backups
umask 077
docker compose exec -T db pg_dump -U setlist --format=custom setlist > backups/setlist.dump
```

Используйте новое имя для каждой копии, храните копии с ограниченным доступом отдельно
от сервера и периодически проверяйте восстановление. Автоматическое расписание копий
в репозитории пока не настроено. Git игнорирует каталог `backups/` и дампы.

Проверка восстановления в отдельную пустую базу, не затрагивающая рабочую:

```bash
docker compose exec -T db createdb -U setlist setlist_restore
docker compose exec -T db pg_restore -U setlist --no-owner --no-acl -d setlist_restore < backups/setlist.dump
```

Если создание базы завершилось ошибкой, не продолжайте восстановление в существующую
базу без проверки её назначения. Не запускайте второго бота на восстановленной копии
с тем же токеном.

ZIP по `/backup` содержит только общие данные коллектива. Личные черновики и Telegram ID
в него не входят, обратный импорт ZIP пока отсутствует. Он не заменяет полный дамп
PostgreSQL для переноса работающего сервиса. Корзина `/trash` позволяет восстановить
данные в течение 30 дней внутри той же базы; она также не заменяет внешнюю копию.
