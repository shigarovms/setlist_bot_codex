# Запуск, обновление и хранение данных

## Что сохраняется в GitHub

Репозиторий содержит исходники, миграции, lock-файл зависимостей, тесты, CI и
документацию. Он не содержит рабочую базу, Telegram-токен или резервные копии.
Токен передаётся через `.env` либо окружение, пример без секрета — `.env.example`.

На момент первого коммита бот запущен в Docker в рабочем облачном окружении Codex.
Это окружение не является настроенным постоянным хостингом: его непрерывная работа
после закрытия сессии не гарантируется. Push в GitHub не выполняет деплой.
Для работы круглосуточно нужен отдельный постоянно доступный сервер и перенос данных.
Для основного экземпляра выбран Timeweb Cloud с Ubuntu 26.04; перенос ещё выполняется.
Автоматический деплой пока не настроен.

Для нового сервера пользователь выбрал чистую базу: переносить данные из прежнего
окружения или из Новосибирска не нужно. Запуск на новой машине пока не подтверждён.

## Развёртывание

Базовый сценарий Docker Compose описан в [README](../README.md). Compose-конфигурация
поставляется для разработки: параметры PostgreSQL заданы явно и требуют отдельной
настройки перед использованием на постоянном сервере.

```bash
docker compose up --build -d
docker compose ps -a
docker compose exec -T bot .venv/bin/setlist-bot --check
```

Сервис `migrate` применяет Alembic-миграции до запуска бота. В приложении используется
polling: на один токен должен работать только один процесс. При переносе на новый
сервер сначала остановите прежний процесс. `restart: unless-stopped` перезапускает
контейнер только при работающем Docker и сохранённом окружении; он не создаёт хостинг.

Если сеть требует доверенный TLS-прокси, используйте `compose.proxy.yaml` и публичный
CA bundle по инструкции README. Проверка сертификатов остаётся включённой.

## Постоянный сервер Timeweb Cloud

### Установщик для чистого сервера

Скрипт [scripts/setup-server.sh](../scripts/setup-server.sh) запускается под root
из интерактивной консоли Ubuntu: `bash scripts/setup-server.sh`. Для скачивания
его отдельной копии используйте raw-ссылку на проверенный коммит этого репозитория,
сохраните файл, затем запустите через bash. Не передавайте токен в аргументах команды.

Установщик устанавливает Docker и Compose, клонирует проект в `/opt/setlist_bot_codex`,
запрашивает BOT_TOKEN скрытым вводом и записывает настройки в `.env` с правами 0600.
Пароль базы создаётся автоматически. Если `.env` уже существует, его секреты сохраняются;
неполные настройки или том без `.env` останавливают установку без удаления данных.

Доступ к Telegram проверяется через `getMe` из контейнера, без запуска polling.
Применяются миграции, проверяется отсутствие прежних прикладных данных. Перед запуском
нужно остановить старый экземпляр и ввести `STOPPED` в ответ на запрос установщика.
Скрипт не умеет останавливать чужой сервер: это действие выполняется отдельно.
Он не импортирует дампы и не удаляет существующие базы или тома.

Проверка завершения включает доступ к PostgreSQL и наличие записи о старте polling.
Скрытый ввод работает только из интерактивной консоли; не запускайте скрипт через
конвейер `curl | bash`. Установщик удаляет из root authorized_keys временные ключи
с комментарием `setlist-deploy-temporary`, добавленные для этой установки, не трогая
другие ключи. Повторный запуск не предназначен для обновления уже используемой базы;
для обновлений служит отдельный раздел ниже.

Установщик создаёт `setlist-backup.service` и `setlist-backup.timer`: ежедневная копия
около 03:30–03:35 по Москве (00:30 UTC плюс задержка до пяти минут). Копии хранятся
локально 14 дней в `backups/`. Новый дамп сначала записывается во временный файл,
проверяется через `pg_restore --list` и только затем публикуется. Ошибка не удаляет
прежние копии. Внешнее хранение и уведомления о сбоях не настраиваются.

Проверки и ручной запуск копии:

```bash
systemctl list-timers setlist-backup.timer
systemctl status setlist-backup.service
journalctl -u setlist-backup.service --no-pager -n 30
systemctl start setlist-backup.service
```

### Ручная подготовка

После клонирования проекта и подготовки `.env` с токеном включите серверный override.
Для свежей базы создайте случайный пароль в hex-формате без вывода в терминал:

```bash
grep -q '^POSTGRES_PASSWORD=.' .env || openssl rand -hex 32 | sed 's/^/POSTGRES_PASSWORD=/' >> .env
grep -q '^COMPOSE_FILE=compose.yaml:compose.production.yaml$' .env || printf '\nCOMPOSE_FILE=compose.yaml:compose.production.yaml\n' >> .env
chmod 600 .env
docker compose config --quiet
docker compose up -d --wait db
```

Не публикуйте содержимое `.env` или полный вывод `docker compose config`: в них есть
секреты. `--quiet` только проверяет конфигурацию и не выводит её содержимое.
`COMPOSE_FILE` сохраняется в `.env`, поэтому следующие вызовы `docker compose` из
каталога проекта автоматически применяют оба файла. Требуется Compose 2.24.4+.

`compose.production.yaml` убирает опубликованный порт PostgreSQL, задаёт один пароль
для базы и обоих клиентов и включает автозапуск базы после перезагрузки Docker.
Сервис бота уже имеет `restart: unless-stopped`. Пароль применяется при первой
инициализации пустого тома; изменение `.env` не меняет пароль существующей базы.

При переносе работающего бота на этом шаге запускайте **только db**. Затем нужно
остановить старый polling, сделать окончательный полный дамп, перенести и восстановить
его, применить миграции и только после этого запустить bot. До остановки источника
можно подготовить доступ и проверить пробное восстановление в отдельной базе.

## Обновление

До изменения схемы сохраните резервную копию. Для простого обновления с паузой в работе:

```bash
docker compose build
docker compose stop bot
docker compose run --rm --no-deps migrate
docker compose up -d --no-build bot
docker compose exec -T bot .venv/bin/setlist-bot --check
docker compose logs --tail 30 bot
```

Эти команды выполняются из каталога нужной версии кода. При использовании TLS-override
применяйте те же `-f compose.yaml -f compose.proxy.yaml` ко всем вызовам Compose.
При ошибке миграции разберитесь с ней до запуска новой версии. Откат кода не означает
безопасный откат схемы: отдельные миграции защищают данные от потери при downgrade.

При старте бот проверяет и синхронизирует команды Telegram до начала polling.
Отдельная команда `setlist-bot --sync-commands` обновляет только меню и не запускает
второй polling-процесс. Области видимости, языки и дополнительные исторические
регистрации описаны в разделе «Меню команд Telegram» README.

## PostgreSQL и резервные копии

Данные хранятся в Docker-томе `postgres_data`; его полное имя зависит от имени
Compose-проекта. Пересоздание контейнера сохраняет том. `docker compose down -v`
удаляет его; эту команду нельзя использовать для обычного обновления.

Полный дамп, включая личные черновики и служебные связи, можно сохранить так:

```bash
mkdir -p backups
chmod 700 backups
umask 077
docker compose exec -T db pg_dump -U setlist --format=custom setlist > backups/setlist.dump
```

Используйте новое имя для каждой копии, храните копии с ограниченным доступом отдельно
от сервера и периодически проверяйте восстановление. При ручной установке расписание
нужно настроить отдельно; установщик выше создаёт локальный ежедневный таймер.
Git игнорирует каталог `backups/` и дампы.

Проверка восстановления в отдельную пустую базу, не затрагивающая рабочую:

```bash
docker compose exec -T db createdb -U setlist setlist_restore
docker compose exec -T db pg_restore -U setlist --no-owner --no-acl -d setlist_restore < backups/setlist.dump
```

Если создание базы завершилось ошибкой, не продолжайте восстановление в существующую
базу без проверки её назначения. Не запускайте второго бота на восстановленной копии
с тем же токеном.

ZIP по `/backup` содержит только общие данные коллектива. Личные черновики и Telegram ID
в него не входят, обратный импорт ZIP пока отсутствует. Он не заменяет полный дамп
PostgreSQL для переноса работающего сервиса. Корзина `/trash` позволяет восстановить
данные в течение 30 дней внутри той же базы; она также не заменяет внешнюю копию.
