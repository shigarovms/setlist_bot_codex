Базы остаются в своих контейнерах/томах. Тестовый дамп в основную базу не загружается.
Пользователи, песни, выступления, черновики и варианты основного бота сохраняются.
Article меняет прежний неявный стиль; аудированный ручной выбор mono сохраняется.

Токены, ключи и роли разных контуров не смешиваются. Основной `.env.miniapp` содержит
производный ключ проверки initData основного бота, не токен Bot API. `.env.calendar`
содержит отдельную read-only роль основной БД. `.env.calendar-key` с Fernet-ключом
доступен только основному bot, не HTTP-сервисам. Все приватные файлы имеют права 600.

Порты 80/443 обслуживает **существующий Caddy** из тестового проекта. Он получает
ещё один hostname и HTTP-only сеть `setlist-public-edge`, не доступ к production DB.
У upstream используются уникальные имена: сервисы с одинаковыми именами calendar/
miniapp в двух проектах не должны выбираться случайно через общий DNS.
Админка остаётся за SSH на 127.0.0.1:8088. Не запускайте второй Caddy на 80/443.

## Перед запуском

Пользователь уже настроил Main Mini App у @setListDuration_bot в BotFather:
`https://setlist-212-192-217-128.sslip.io/miniapp/`.

Код публикуется отдельно от работающего VPS. Из облачной среды SSH сейчас получает
Connection refused, поэтому следующие команды выполняет владелец в своей консоли.
Обновления выполняются последовательно на одном сервере, не параллельно.

## Обновить основной бот

```bash
(
  set -e
  # Получаем только исходники прокси; тестовый polling не перезапускается.
  cd /opt/setlist_bot_sandbox
  test -z "$(git status --porcelain)"
  git switch feature/web-admin
  git pull --ff-only origin feature/web-admin

  cd /opt/setlist_bot_codex
  test -z "$(git status --porcelain)"
  git switch main
  git pull --ff-only origin main
  git log -1 --oneline
  bash scripts/release-production.sh
  python3 scripts/setup-production-public.py
)
```

Первый скрипт собирает образы. Пока основной бот работает, делает резервную копию
**основной базы**, восстанавливает её в новую временную `setlist_admin_release_*_test`
на том же VPS и репетирует миграции. Проверяет сохранность числа строк основных
таблиц и новую схему. После успеха удаляет только эту временную копию.

Затем останавливает основной bot (и уже установленные основные HTTP-сервисы), делает
ещё одну свежую резервную копию, применяет миграции к существующей `setlist`, проверяет
схему и запускает сервисы. Рабочая БД не пересоздаётся и не восстанавливается из дампа.

Второй скрипт проверяет основной token/DB ID, создаёт отдельные основные роли и ключи,
запускает calendar/miniapp и проверяет внутренний health. Добавляет hostname к общему
прокси, ждёт готовности HTTPS **обоих контуров**, затем включает адреса в основном bot.
Тестовый bot, его БД и admin этим установщиком не пересоздаются. Возможен короткий
перезапуск общего Caddy; данные и polling двух ботов от этого не меняются.

Нормальный финал: `Production calendar and Mini App ready: https://setlist-212-192-217-128.sslip.io`.
При сбое HTTPS основной bot не получает новые ссылки этим шагом; исправьте причину
и повторите только `python3 scripts/setup-production-public.py`. Пароли/ключ сохранятся.
После настройки COMPOSE_FILE основного проекта включает `compose.public.production.yaml`.

**Сохраните частную копию `.env.calendar-key` отдельно от дампа БД.** Если файл потерян
при существующих шифртекстах, скрипт требует восстановить прежний ключ и не создаёт новый.
Не отправляйте `.env.*`, дампы или вывод `docker inspect` с переменными окружения в чат.

## Проверка после выпуска

Перед публикацией проверено в облачной среде: 500 Python-тестов и 5 JavaScript-тестов,
Ruff, форматирование, mypy, синтаксис shell-скриптов и актуальность lock-файла.
Проверены итоговая Docker Compose-конфигурация и конфигурация Caddy. Отдельный
интеграционный запуск Caddy с двумя временными HTTP-контурами подтвердил маршрутизацию
обоих hostname при совпадающих служебных DNS-именах и отсутствие публичного `/admin`.
Это не проверка TLS или работающего обновления на VPS: их выполняет установщик ниже.

1. В основном @setListDuration_bot: `/start`, `/concerts`, существующий коллектив,
   свои прежние выступления/песни и утверждённый PDF. Тестовые данные там не появляются.
2. Создайте своё проверочное выступление новым вводом; проверьте все поля до подтверждения.
3. Редактор в основной личке и группе: свой черновик, повторения, паузы, автосохранение,
   отправка предложения и закрытие после доставки. Сам общий список не заменяется.
4. `/calendar`: основной URL начинается с `https://setlist-212-192-217-128.sslip.io/`.
   Тестовый URL остаётся прежним. Проверьте подключение и повторный показ ссылки.
5. Откройте тестового бота: его данные и возможности остаются своими. Через прежний

Диагностика без секретов:

основной БД при ошибке: сохраните резервные копии и разберите конкретный этап.

## Последующие обновления

Основной проект: `git pull --ff-only origin main`, затем `bash scripts/release-production.sh`.
Скрипт автоматически учитывает уже подключённые HTTP-сервисы и останавливает их на
время финальной копии/миграции. После смены токена основного бота повторите
`python3 scripts/setup-production-public.py` для обновления производного ключа.

Тестовые скрипты обновления/установки сохраняют дополнительный hostname и сеть Caddy
по маркеру `.env.production-public`. Он содержит только hostname. Не удаляйте его при
обновлении тестового контура. Не запускайте старые инструкции с пересозданием proxy
без `compose.proxy.production-access.yaml`: штатные скрипты добавляют его автоматически.
