# Веб-админка тестового бота

Админка — отдельный HTTP-сервис на Python/aiohttp. Она работает с той же PostgreSQL,
что и выбранный бот, но не запускает polling и не получает Telegram-токен.
Для начала предназначена для **@botToPract696_bot** и базы **setlist_sandbox**.
Основная база и токен @setListDuration_bot не подключаются.

## Возможности

- Обзор: пользователи, действующие коллективы, предстоящие мероприятия, открытые
  обращения, очередь/ошибки, активность обновлений и доставка за 24 часа.
- Поиск и пагинация по 25 строк для пользователей, коллективов, мероприятий,
  каталога, обращений, очереди и аудита. Содержимое PDF не загружается для статистики.
- Пользователь: Telegram ID, язык, членство и имена в коллективах; последняя
  активность доступна после установки мониторинга. Личные черновики не раскрываются.
- Коллектив: владелец, участники/права, каталог, мероприятия, напоминания. Передача
  владения принятому участнику требует точного названия и проверки старого владельца.
  Использовать только после проверки обращения. Прежний владелец остаётся администратором.
- Общие рабочие/утверждённые списки, подпись одобрения, песни/паузы и длительности.
- Поддержка: текст обращения, ответ через существующую очередь бота, история и статус
  доставки, открытие/закрытие обращения. Двойная отправка одной формы не дублирует ответ.
- Очередь: код ошибки, число попыток, время следующего повтора, повтор/исключение
  с подтверждением. Доставленные сообщения повторно отправить через админку нельзя.
- Восстановление коллектива/мероприятия из корзины с прежними проверками срока
  хранения, прав владельца и свободной привязки чата. Окончательное удаление не добавляется.
- Аудит изменений и управление сессиями. Один владелец веб-аккаунта, без публичной
  регистрации. Интерфейс первой версии русский; интерфейс Telegram остаётся RU/EN.
- Состояние процесса, фоновых задач и ошибок polling; отдельный сигнал активности
  и следующий запуск. Отчёт хоста даёт диск, RAM, нагрузку и свежесть копии.

## Принцип мониторинга и границы

Сигналы процесса и задач пакетно сохраняются каждые 30 секунд. Это отдельный процесс
бота, а не состояние HTTP-сервиса. Остановленный бот становится виден как устаревший
сигнал. Живой процесс сам по себе не доказывает доступность Telegram. Ошибки получения
обновлений и отправок учитываются отдельно; содержимое сообщений в метрики не попадает.
При сбое доставки событие откладывается с увеличением интервала; другие события
продолжают отправляться. Неисправимые события можно исключить через админку.
Доставка остаётся «не менее одного раза»: авария после Telegram send до commit БД
может дать дубль, Bot API не поддерживает идемпотентный ключ отправки.

Историческим записям не придумываются даты: старая обработанная отправка без времени
доставки обозначается «Обработано», а не «Доставлено». Графики начинаются с установки.
История ответов до обновления может не иметь привязки к обращению: перед ответом
на старую заявку проверьте чат поддержки. Сессия действует до 8 часов. Обзор кешируется на 20 секунд, браузер обновляет числа
раз в 30 секунд только на видимой вкладке. Пул админки ограничен пятью соединениями,
SQL — восемью секундами. Контейнер ограничен 256 МБ и 0.75 CPU.

1000 зарегистрированных пользователей не означают 1000 одновременных администраторов.
Для этого объёма предусмотрены ограниченные выборки и индексы; тесты проверяют 1005
пользователей и конкурентные запросы. Это не нагрузочный SLA. Реальный лимит зависит
от активности пользователей, импорта и особенно PDF. Начальный ориентир для сервера
с PostgreSQL, ботом и админкой: 2 vCPU и 2–4 ГБ RAM, с наблюдением за фактической нагрузкой.

Нет доступа к Docker socket, запуску произвольных команд, полным дампам и SQL-консоли.
Перезапуск контейнеров выполняется через SSH. Внешние аварийные уведомления и
мониторинг с отдельного сервера в эту версию не входят.

## Можно ли использовать тот же сервер и нужен ли домен

Да. Рекомендуемая схема на 212.192.217.128:

```
/opt/setlist_bot_codex       основной бот и его база (без изменений)
/opt/setlist_bot_sandbox     тестовый бот, отдельная база и веб-админка
```

Compose-проекты и тома раздельные. Админка публикуется только на 127.0.0.1:8088,
PostgreSQL песочницы — только на 127.0.0.1:5433. В Интернет эти порты не открывать.

**Покупать домен не нужно.** Для личного доступа используется SSH-туннель. Его
шифрование защищает HTTP между вашим компьютером и сервером. Без туннеля адрес
127.0.0.1:8088 на вашем Mac не относится к серверу.

Если позже понадобится постоянный публичный адрес, можно использовать поддомен
существующего домена, HTTPS через reverse proxy и WEB_ADMIN_SECURE_COOKIE=true,
добавив домен в WEB_ADMIN_ALLOWED_HOSTS. Не публикуйте парольную админку обычным
HTTP по IP. Админка сама не устанавливает Caddy/Nginx и сертификаты.

## Установка отдельного тестового контура на VPS

Код веб-админки находится в ветке **feature/web-admin**, а не автоматически в main.
Не выполняйте установку песочницы в каталоге основного бота.

На сервере:

```bash
cd /opt
git clone --branch feature/web-admin https://github.com/shigarovms/setlist_bot_codex.git setlist_bot_sandbox
cd /opt/setlist_bot_sandbox
bash scripts/prepare-sandbox-admin.sh
```

Если каталог уже существует, сначала проверьте его назначение и `git status`; не
запускайте clone повторно поверх существующих файлов. Установка потребует Docker
Compose и Python 3, уже имеющихся на текущем сервере.

Скрипт скрыто запрашивает **тестовый** токен и проверяет ID 1110437563. Основной токен
отвергается; в контейнере бота дополнительно проверяется EXPECTED_BOT_ID до polling.
Потом строит образы, поднимает отдельную БД, делает копию существующей песочницы,
применяет миграцию, запрашивает логин/пароль админки (не короче 12 символов) и запускает
только веб-сервис. Пароль хранится как scrypt-хеш в .env.admin, файл имеет права 600.
Токен находится в отдельном .env. Оба файла исключены из Git и Docker build context.

**Сам polling скрипт не запускает.** Один тестовый токен нельзя одновременно
запускать здесь и в облачной среде Codex. Сначала нужно остановить прежний тестовый
экземпляр. Если нужны его данные, перенести следует отдельный дамп setlist_sandbox
в новую тестовую базу ДО её использования. Он никогда не восстанавливается в setlist.
Перенос данных и переключение polling согласовываются отдельно; первоначально новая
песочница на VPS пуста, веб-сервис не сможет видеть старую облачную базу автоматически.

Когда старый тестовый экземпляр остановлен и вопрос данных решён:

```bash
cd /opt/setlist_bot_sandbox
docker compose -f compose.sandbox.yaml up -d --no-build --no-deps bot
docker compose -f compose.sandbox.yaml exec -T bot .venv/bin/setlist-bot --check
```

## Открыть на Mac

В отдельном окне Терминала **на Mac**, оставив его открытым:

```bash
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:8088:127.0.0.1:8088 root@212.192.217.128
```

Откройте **http://127.0.0.1:8088** в браузере и введите выбранные при установке логин
и пароль. Пустой терминал при `ssh -N` нормален: он держит туннель. Ctrl+C закроет
доступ из браузера, но админка и бот на сервере продолжат работать.
Если порт на Mac занят, замените первую 8088 на 18088 и откройте http://127.0.0.1:18088.

## Подключить отчёт хоста и копии песочницы

Первый отчёт создаёт установочный скрипт. Чтобы он обновлялся каждую минуту,
на сервере можно добавить отдельные systemd units (имена не пересекаются с production):

```bash
cat > /etc/systemd/system/setlist-sandbox-admin-status.service <<'UNIT'
[Unit]
Description=Setlist sandbox host metadata
[Service]
Type=oneshot
WorkingDirectory=/opt/setlist_bot_sandbox
ExecStart=/usr/bin/python3 /opt/setlist_bot_sandbox/scripts/admin-host-status.py --directory /opt/setlist_bot_sandbox
UNIT
cat > /etc/systemd/system/setlist-sandbox-admin-status.timer <<'UNIT'
[Unit]
Description=Update sandbox admin host status
[Timer]
OnBootSec=30s
OnUnitActiveSec=60s
[Install]
WantedBy=timers.target
UNIT
systemctl daemon-reload
systemctl enable --now setlist-sandbox-admin-status.timer
```

Отчёт содержит только технические числа и имя/возраст копии. Он подключается к
контейнеру только для чтения; сами дампы не монтируются. Проверяйте дату отчёта.

Копия тестовой базы вручную:

```bash
SETLIST_SANDBOX_DIR=/opt/setlist_bot_sandbox bash /opt/setlist_bot_sandbox/scripts/backup-sandbox.sh
```

Скрипт production-копий для тестовой базы не использовать. Копии песочницы автоматически
не удаляются; настройте срок хранения и внешний диск отдельно. Ежедневный таймер
основной базы остаётся прежним и не заменяется.

## Обслуживание веб-сервиса

Из /opt/setlist_bot_sandbox:

```bash
# Состояние и журнал только админки
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml ps admin
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml logs --tail 60 admin

# Перечитать изменённую .env.admin
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml up -d --no-build --no-deps --force-recreate admin

# Остановить только веб-интерфейс; бот продолжит работу
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml stop admin
```

Пароль, хеш, подпись сессий и адрес БД не отправляйте в чат. Для сброса пароля
создайте новый файл через ту же CLI-команду `--create-config`, проверьте адрес
тестовой БД, замените .env.admin и пересоздайте контейнер. Смена WEB_ADMIN_SECRET
отменяет старые сессии; кнопка «Завершить все сессии» делает это без смены файла.

Миграция **a924c61d08be** добавляет аудит, сессии, статусы, обращения и метаданные
доставки; песни/концерты/черновики не переписываются. Откат с новым аудитом и
связанными ответами поддержки запрещается, чтобы не потерять историю.

## Запуск в облачной песочнице разработчика

Из существующего проекта используются те же compose.sandbox.yaml и отдельный
compose.admin.sandbox.yaml; при сборке в сети с TLS-прокси добавляется compose.proxy.yaml.
Сначала новая миграция и обновление тестового бота, затем сервис admin с --no-deps.
В образе нет выбранного пароля или .env.admin. База автоматических тестов — только
setlist_test. Работа в облачной среде не обещает публичной ссылки или круглосуточного
хостинга; для браузера владельца нужна серверная схема выше.
