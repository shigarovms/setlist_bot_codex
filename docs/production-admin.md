# Подключение основной базы к веб-админке

Один VPS 212.192.217.128: основной бот `/opt/setlist_bot_codex`, тестовый контур
и веб-сервис `/opt/setlist_bot_sandbox`. Переключатель уже реализован. Для основного
раздела нужны совместимый код бота, миграция и отдельное подключение БД.
Доступ из браузера остаётся через существующий SSH-туннель с Mac. Соединение
облачной среды Codex с VPS не требуется.

## Что сохраняется раздельным

- Основная база — `setlist`, тестовая — `setlist_sandbox`, в разных контейнерах/томах.
- Дампы тестового контура никогда не восстанавливаются в основном.
- Админка не получает Telegram-токены. Для основной БД создаётся роль
  `setlist_web_admin` с собственным случайным паролем, без SUPERUSER/CREATEDB/CREATEROLE.
- Содержимое личных черновиков и PDF этой роли недоступно. Разрешены только чтение
  нужных таблиц, служебные записи входа/аудита и изменения существующих действий админки.
  У роли нет удаления/очистки каталога, произвольного создания таблиц или владения ими.
- Режим просмотра дополнительно ограничен PostgreSQL. Повторный запуск без
  `--enable-actions` снимает ранее выданные права изменения основных таблиц.
- Сессии, подписи, кеши и формы привязаны к выбранному контуру. Пароль веб-входа
  прежний; в основном разделе потребуется отдельный вход.

## 1. Обновить основной бот

Убедитесь в чистом рабочем дереве. Выполнять на VPS, в консоли root:

```bash
cd /opt/setlist_bot_codex
git status --short
git pull --ff-only origin main
bash scripts/release-production.sh
```

Если status показывает ваши изменения, сначала сохраните их; не применяйте reset.
Скрипт проверяет каталог/ветку/ID основного бота и собирает новый образ. Пока старый
бот продолжает работать, делает резервную копию, восстанавливает её в **новой
временной базе `setlist_admin_release_*_test` на том же VPS**, применяет миграции
и проверяет сохранность количества строк основных таблиц. Эта копия никуда не уходит.

При успехе удаляет только временную базу, останавливает основной bot, сохраняет
ещё одну свежую копию, обновляет основную схему и запускает новый bot. База `setlist`
не удаляется, не пересоздаётся, дамп в неё не восстанавливается. Каталоги тестового
бота и его БД не участвуют в выпуске.

При ошибке до остановки основной бот продолжает работать. При ошибке миграции после
остановки новый код не запускается; резервные копии остаются. Не делайте автоматический
downgrade/восстановление поверх изменившейся основной базы: сначала разберите ошибку.

Проверьте `/start` основного @setListDuration_bot. При проблемах:

```bash
docker compose -f compose.yaml -f compose.production.yaml logs --tail 50 bot
```

## 2. Подключить существующую админку

После успешного выпуска основного бота, на том же VPS:

```bash
cd /opt/setlist_bot_sandbox
git status --short
git pull --ff-only origin feature/web-admin
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml \
  build --build-arg "APP_REVISION=$(git rev-parse HEAD)" admin
python3 scripts/connect-production-admin.py --enable-actions
```

Подключение проверяет схему, привязку к Telegram ID 7430933141 и свежий сигнал
совместимого production-процесса. Если процесс только запустился, дождитесь сигнала
и повторите последнюю команду. Параметр `--enable-actions` включает существующие
административные действия. Без него подключение открывается для просмотра.

Скрипт создаёт отдельную PostgreSQL-роль, записывает её URL только в `.env.admin`
с правами 600 и делает приватную резервную копию исходного файла. При прерывании
подготовки пароль сохраняется в приватном `.env.admin.production-pending`, чтобы
повторный запуск не сбрасывал неизвестные учётные данные. Не публикуйте `.env.*`.

Затем подключает только admin к внутренней production-сети через
`compose.admin.production-access.yaml` и пересоздаёт только этот веб-контейнер.
Порты PostgreSQL не открываются в Интернет. Имена контейнеров в URL явные, чтобы
два сервиса с именем `db` не перепутались. Работающие боты этим шагом не перезапускаются.
Успех печатается только после проверки `/sandbox/healthz` и `/production/healthz`.

Для основного раздела используется свой отчёт резервных копий. Отдельный
`setlist-production-admin-status.timer` обновляет технические метаданные каждые
60 секунд, не заменяя `setlist-backup.timer`. В admin монтируются только эти
метаданные, не содержимое резервных копий и не Docker socket.

## 3. Проверить в браузере

Обновите страницу админки, нажмите «Основной» и войдите прежним логином/паролем.
Проверьте свои коллективы/мероприятия и мониторинг: ID 7430933141, контур production,
место production-server, актуальные ревизия и схема. Переключитесь обратно в тестовый:
там должны оставаться только тестовые данные.

Создайте своё тестовое обращение в поддержку основного бота и ответьте через основной
раздел админки. Это проверит доставку без изменения чужих песен/концертов. Историческая
активность до установки мониторинга не восстанавливается задним числом.

При неполадках смотрите только журнал admin:

```bash
cd /opt/setlist_bot_sandbox
docker compose -f compose.sandbox.yaml -f compose.admin.sandbox.yaml \
  -f compose.admin.production-access.yaml logs --tail 50 admin
```

При следующих перезапусках веб-сервиса сохраняйте все три `-f`, чтобы осталось
подключение к основной сети. Для нового действия админки отдельно проверяйте и
расширяйте SQL-права роли; не заменяйте её владельцем базы ради обхода ошибки доступа.
