# Бот, админка и переключение места запуска

Согласовано 28 октября 2026. Код находится в `feature/web-admin`; публикация ветки
сама по себе не обновляет сервер. Основной контур не мигрируется автоматически.

## Что изменилось

1. В мониторинге показываются Telegram ID/username, контур, место запуска,
   Git-ревизия, время старта, идентификатор экземпляра и версия схемы. В Docker
   ревизия записывается при сборке через `--build-arg APP_REVISION=...`; без неё
   честно показывается `unknown`. Локальный запуск читает ревизию checkout.
2. Бот перед обращением к Telegram проверяет точное совпадение схемы с
   `infrastructure/runtime.py:SCHEMA_REVISION`. Админка также проверяет схему,
   кешируя результат на 20 секунд. Несовпадение даёт понятный отказ, не попытку
   работать с неполной схемой.
3. Управление напоминаниями и передача владения используют общие методы `Groups`;
   восстановление — прежний `Trash`, ответы поддержки — прежний `Support`.
   Права перечитываются после получения блокировки коллектива.
4. Изменения данных ставят задания обновления существующих общих карточек в outbox.
   Используются обычные рендеринг, `editMessageText` и привязка ответов к сообщению.
   Устаревшие/закрытые карточки, личные черновики и исторические версии не обновляются.
   Несколько изменений объединяются в одно ожидающее задание на карточку; при импорте
   список карточек читается один раз после всего пакета. Недоступность Telegram не
   откатывает уже сохранённое изменение: доставка повторяется с прежним backoff.
5. Журнал показывает источник `telegram`/`web` и реального автора. В нём нет текстов
   обращений, комментариев песен или личных черновиков. Ответы поддержки сохраняют
   автора/источник в общей истории. Версия обращения увеличивается при ответе или
   изменении статуса: устаревшая веб-форма получает конфликт. Дополнительный ответ
   после обновления страницы разрешён. Telegram Reply сохраняет текущий статус
   обращения; закрытие/открытие выполняется явным действием в админке.
6. У компонентов есть отдельные времена успеха и ошибки. Успешный пустой getUpdates
   подтверждает доступность Telegram, но не считается активностью пользователя.
   Видны возраст очереди и последняя подтверждённая доставка. Сигналы сохраняются
   пакетно каждые 30 секунд; это не мгновенный внешний мониторинг.

Миграция `c14f802d9a63` расширяет диагностику, поддержку и аудит, добавляет привязку
БД к боту и индекс запросов по чату. Песни, концерты, версии, черновики и PDF не
переносятся и не переписываются. Откат отказывается удалять привязку, события аудита,
состояние ответов и ожидающие задания нового типа. Перед миграцией нужна копия.

## Два контура в одном браузере

Веб-сервис открывает `/sandbox/` и, если подключён, `/production/`. Старые GET-адреса
перенаправляются в тестовый контур; старые POST-формы нужно открыть заново.
Подключения, кеши, cookies и подписи форм у контуров раздельные. Один логин/пароль
может использоваться для обоих, но вход выполняется отдельно в каждом. Переключение
не меняет глобальное состояние сервера и не перенаправляет уже открытую форму.

Без настройки основной БД показывается «Основной ещё не подключён». Автоматического
открытия тестовых данных вместо основных нет. Пароль и подпись берутся из прежнего
`.env.admin`; менять их при обновлении не нужно, но потребуется повторный вход.

Подключение production согласовано отдельно; выполняется после резервной копии,
проверки миграций на копии и обновления основного бота по
[инструкции выпуска](production-admin.md). Для подключения предусмотрены:

- `WEB_ADMIN_PRODUCTION_DATABASE_URL` — отдельный секретный URL основной БД;
- `WEB_ADMIN_ALLOW_PRODUCTION=true` — явное разрешение подключения;
- `WEB_ADMIN_PRODUCTION_READ_ONLY=true` — значение по умолчанию;
- `compose.admin.production-access.yaml` — подключение только admin к существующей
  production-сети. Адрес тестовой БД фиксируется именем контейнера, чтобы два сервиса
  с именем `db` в разных сетях не перепутались. Токен бота админке не передаётся.

Даже при снятом read-only изменения запрещены без свежего сигнала от production-бота
7430933141 с нужной схемой и контуром. Проверка только номера миграции недостаточна:
старый worker не умеет обрабатывать новые задания обновления карточек.

## Обновить тестовый сервер

Только из `/opt/setlist_bot_sandbox`, после проверки изменений и публикации ветки:

```bash
cd /opt/setlist_bot_sandbox
git status --short
git pull --ff-only origin feature/web-admin
bash scripts/update-sandbox-admin.sh server
```

Не продолжайте после ошибки или при своих незакоммиченных изменениях. Скрипт сначала
собирает общий образ, затем останавливает только тестовые сервисы, сохраняет копию,
мигрирует, проверяет БД и запускает admin и bot. При ошибке миграции не запускает
новый код; копия остаётся в `backups`. Это не скрипт восстановления данных.

## Тестовая БД на сервере, бот в облачной среде

База `setlist_sandbox` и веб-админка остаются на VPS. Меняется только процесс polling.
Дампы между местами запуска не переносятся. PostgreSQL остаётся закрыт от Интернета;
SSH переносит локальный порт облачной среды на `127.0.0.1:5433` сервера.

Для подключения нужен разрешённый исходящий SSH из облачной среды. На момент
подготовки кода прямой TCP/22 получил отказ, а штатный прокси — HTTP 403. Добавление
IP в черновик разрешённых адресов ещё не означает применения настройки или поддержки
произвольного TCP. Пока связь не проверена, серверный бот продолжает работать.
Не устанавливайте VPN-клиент или публичный PostgreSQL для обхода сетевой политики.

После разрешения связи на сервере один раз настраивается ограниченный пользователь:

```bash
cd /opt/setlist_bot_sandbox
bash scripts/setup-sandbox-tunnel.sh /путь/к/публичному-ключу.pub
```

Скрипт принимает обычный ED25519 public key. У аккаунта `setlist-tunnel` нет доступа
к shell/TTY, разрешено только локальное перенаправление к `127.0.0.1:5433`.
Root-доступ и процессы ботов он не меняет. Проверяет sshd-конфигурацию до reload.
Публичный host key сервера сверяют с заранее известным отпечатком:

```text
SHA256:XREWC8TDKC91pNFnjmaR/9nSvXMrBKGiOugvqfhLaa0
```

В приватном файле вне Git на машине разработки задаются:

```dotenv
BOT_TOKEN=<только тестовый токен, ввести локально>
DATABASE_URL=postgresql+asyncpg://setlist:setlist@127.0.0.1:15433/setlist_sandbox
EXPECTED_BOT_ID=1110437563
RUNTIME_ENVIRONMENT=sandbox
RUNTIME_LOCATION=codex-cloud-over-ssh
```

Файл и закрытый SSH-ключ должны иметь права 600. `known_hosts` содержит фактический
проверенный публичный ключ, а не только его отпечаток. Не отправляйте приватные файлы
в чат и не храните их в репозитории.

Сначала на VPS обновляют тестовый контур и оставляют polling остановленным:

```bash
bash scripts/update-sandbox-admin.sh cloud
```

Затем в облачной среде проверяют туннель и совместимость БД без Telegram polling:

```bash
cd /workspace/setlist_bot_codex
.venv/bin/python scripts/run-cloud-sandbox.py \
  --env-file /private/sandbox.env \
  --identity /private/id_ed25519 \
  --known-hosts /private/known_hosts \
  --check-only
```

Только после успешной проверки запускают ту же команду без `--check-only`.
Это foreground-процесс, который нужно держать через менеджер процессов среды;
закрытие его терминала или остановка среды не гарантируют продолжение работы.
Супервизор останавливает polling при завершении SSH. Бот также держит отдельную
PostgreSQL session lock: потеря её соединения завершает polling, а не переподключает
его незаметно. Два обновлённых экземпляра одной БД одновременно не запустятся.
Такая блокировка не защищает старый код или две независимые копии БД: передача
polling всё равно выполняется явно, с остановкой прежнего процесса.

Возврат на VPS: остановить облачный супервизор и проверить отсутствие polling,
затем на сервере запустить `docker compose -f compose.sandbox.yaml up -d --no-build
--no-deps bot`. База и данные остаются прежними.
