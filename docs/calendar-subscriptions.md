# Календарные подписки — тестовый выпуск, 31 октября 2026

Первый этап: односторонняя подписка Google Calendar / Apple Calendar.
Изменения выполняются в боте. Аккаунт Google, Apple ID и пароли не запрашиваются.
OAuth и запись событий из календарных приложений в бот не реализованы.

## Подключение пользователем

1. В личке тестового бота отправьте `/calendar` или `/all_my_concerts` → «Подключить календарь».
2. Выберите все свои выступления или конкретный коллектив → «Подключить».
3. Скопируйте персональный HTTPS-адрес. Секрет показывается при создании, в БД только
   хеш случайного 256-битного значения. Не передавайте ссылку другим.
4. В Apple Calendar добавьте календарь по подписке. В Google Calendar откройте
   веб-версию → Другие календари → «+» → Добавить по URL. Вставьте ссылку: подписка
   появится и в мобильном приложении. Не используйте разовый импорт файла `.ics`.
5. Дайте календарю удобное имя/цвет. Выберите общий календарь или отдельные по группам;
   подключение одной группы обоими способами может дать дубликаты в разных календарях.

События всегда на весь день, без часового пояса. Название содержит коллектив и
выступление, местоположение — город. Описание: тип, плановая длительность и
дополнительная информация. Начало/окончание пишите в дополнительной информации,
например `Начало: 20:00; окончание: 21:40`: временные границы события не меняются.
Ссылка события открывает выступление в личке бота с повторной проверкой доступа.
Нет песен, личных черновиков, переписки и аккаунтов участников.

Общий календарь включает все активные членства, независимо от роли. Администратор
трёх групп и участник ещё двух видит все пять, но меняет только разрешённые ему
данные в боте. Новые подтверждённые членства включаются автоматически. Корзина и
неподтверждённые/отозванные членства не передаются в календарь.

Google/Apple определяют расписание обновления сами, иногда с существенной задержкой.
Рекомендация обновлять раз в час не гарантирует мгновенную доставку. После удаления
выступления оно отсутствует в полной свежей выдаче; календарное приложение должно
обновить свою копию. Уже скачанные данные нельзя стереть с устройства принудительно.

`/calendar` → «Мои подписки»: перевыпуск ссылки или отключение с подтверждением.
Старая ссылка перестаёт обслуживаться; новая добавляется в приложение заново.
Отмена оставляет прежнюю рабочей. Повтор кнопки не создаёт дубликат и не перевыпускает
ссылку повторно. Если сообщение со ссылкой потеряно, используйте перевыпуск.
После отключения удалите ненужный календарь и из приложения — старый кэш может остаться.

## Устройство и ограничения

- `domain/calendar.py`: RFC 5545, UID по боту/выступлению, SEQUENCE по версии метаданных
  и жизненного цикла, VALUE=DATE и исключительная дата окончания. DTSTAMP — время
  генерации календарного объекта, не выдуманная дата изменения истории. Экранирование
  текста и folding по 75 октетов сохраняют UTF-8 и запрещают инъекцию новых событий.
- `application/calendars.py`: один scope на пользователя/коллектив или все группы;
  только SHA-256 секрета. Подтверждения привязаны к владельцу, чату, версии, сроку 10 минут.
  Аудит не содержит ссылки и её хеша.
- `calendar/app.py`: отдельный aiohttp, только GET/HEAD выдачи. Членство/корзина
  проверяются перед кешем и If-None-Match. Weak ETag учитывает смысл данных и не
  заставляет скачивать календарь только из-за нового DTSTAMP после перезапуска.
- Не более 128 ответов / 8 MiB кеша, 5000 событий / 4 MiB ответа. Превышение даёт
  503 без молчаливого обрезания. Четыре одновременных запроса, перегрузка 503/Retry-After;
  очередь не растёт неограниченно. SQL-пул из двух подключений, таймауты, read-only.
- Выделенная SQL-роль читает только нужные таблицы/столбцы. Нет users, черновиков,
  переписки, поддержки, админских сессий и прав записи. Сервис не получает токен
  Telegram или `.env.admin`, проверяет ID/контур БД. Нет внешних запросов по данным пользователя.
- Caddy публикует только `/calendar/*.ics`, не админку и не health. Access log
  приложения выключен; request/uri удаляются из журналов Caddy. Лимиты контейнеров:
  calendar 192 MiB / 0,5 CPU, Caddy 128 MiB / 0,5 CPU — верхние пределы, не постоянная нагрузка.

## Подготовленный выпуск на VPS

Бесплатный адрес: **https://212-192-217-128.sslip.io**, DNS указывает на IP VPS.
Доступность зависит от внешнего DNS-сервиса; сертификат автоматически выдаёт/обновляет
Caddy. При смене домена клиентам потребуется новая ссылка или сохранённый редирект.

Миграция **a82cd901be45 → b93e2a6f104c** добавляет только `calendar_subscriptions`.
Песни, выступления, права, черновики и PDF не переписываются. FK очищает ссылки
при окончательном удалении коллектива/аккаунта. Downgrade с активными ссылками запрещён.
Данные баз между контурами не копируются.

Команды — после публикации согласованного коммита в feature/web-admin, на VPS:

```bash
(
  set -e
  cd /opt/setlist_bot_sandbox
  test -z "$(git status --porcelain)"
  git switch feature/web-admin
  git pull --ff-only origin feature/web-admin
  git log -1 --oneline
  bash scripts/update-sandbox-admin.sh server
  python3 scripts/setup-sandbox-calendar.py --host 212-192-217-128.sslip.io
)
```

Облачный polling уже остановлен. Скрипт обновляет существующий серверный тестовый
бот, сохраняет **его собственную серверную БД**, мигрирует и проверяет её. Основной
Telegram-бот/БД не обновляются. Установщик создаёт read-only роль, записывает секрет
в `.env.calendar` (600), сохраняет частные копии настроек, добавляет публичный адрес
в `.env`, запускает calendar/Caddy и проверяет HTTPS. Только после этого пересоздаёт
тестового бота с подключённой кнопкой. Повторный запуск сохраняет существующий пароль;
при потере конфигурации отказывается сбрасывать пароль. `.env.admin` не меняется.

TCP **80 и 443** должны быть свободны и открыты в облачном firewall. 80 нужен для
сертификата/редиректа, 443 — для подписки. PostgreSQL и админка наружу не открываются.
Если HTTPS не готов, настройка остановится до пересоздания бота: проверьте DNS/firewall
и повторите установщик. При последующих обновлениях `.env.calendar` автоматически
подключает Compose override и остановку читателя до миграции.

Проверки на VPS:

```bash
cd /opt/setlist_bot_sandbox
docker compose -f compose.sandbox.yaml -f compose.calendar.sandbox.yaml ps calendar calendar_proxy
docker compose -f compose.sandbox.yaml -f compose.calendar.sandbox.yaml exec -T calendar \
  .venv/bin/python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8090/healthz').status)"
curl -I https://212-192-217-128.sslip.io/calendar/check.ics
```

Ожидаются внутренний health `200` и внешний HTTPS `404` для вымышленной ссылки.
Настоящий секретный URL не отправляйте публичным анализаторам и не включайте в журналы.
Админка остаётся на 127.0.0.1:8088 за прежним SSH-туннелем.

Новый тестовый admin требует b93e2a6f104c: основной раздел временно покажет
несовместимую схему до отдельно согласованного обновления production. Основной
Telegram-бот продолжит работать. При ручных Compose-командах сохраняйте календарный
override и `compose.admin.production-access.yaml`, если подключена основная админка.

## Проверки

1. Подпишитесь на все выступления и проверьте даты на весь день, описание и ссылку в бот.
2. Измените город/название/дополнительную информацию, дождитесь обновления. Нет дубликата.
   Удалите тестовое выступление и проверьте свежую выдачу/задержку своего приложения.
3. Отдельный коллектив не показывает остальные. Участник подписывается без выдачи прав админа.
4. Отмена перевыпуска сохраняет старую ссылку, подтверждение заменяет её. Повтор безопасен.
5. Отключение ссылки не меняет песни/выступления. Проверьте отзыв членства на втором аккаунте.

Полный локальный прогон: **443 теста прошли**, включая миграции и реальную read-only
SQL-роль. Ruff, форматирование, mypy и lock-файл проверены; конфигурация Caddy валидна.
Автотесты используют только отдельную `_test`-базу и подменённый Telegram.
Публичный сертификат и настоящие приложения Google/Apple проверяются на VPS;
локальный прогон не означает, что сторонний календарь уже обновился.
